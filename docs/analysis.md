# บทวิเคราะห์นโยบาย CSC-ONE

วิเคราะห์เมื่อ 20 พฤศจิกายน 2569 ใช้ประกอบการจัดทำ [ร่างนโยบาย](../policy/CSC-ONE-policy.md)

## แนวคิดตั้งต้น

นโยบายด้านการบริหารจัดการงานเทคโนโลยีสารสนเทศ 4 ด้าน:

- **One Data Service** รวมระบบ MIS เพื่อการตัดสินใจของผู้บริหาร
- **One Audit** log และการเฝ้าระวัง เพื่อการตรวจสอบตามมาตรฐาน audit และ PDPA
- **One Stop Service** รวมระบบสารสนเทศให้เข้าถึงบริการได้จากที่เดียว
- **One Architecture** มาตรฐานการพัฒนาระบบสารสนเทศ

เป้าหมายคือรวบรวมข้อมูลและบริการทั้งหมดของวิทยาเขตไว้ที่เดียว นำไปสู่ **One-Brain** คลังความรู้ของวิทยาเขต

## สิ่งที่ปรับจากแนวคิดตั้งต้น

1. **One Architecture เป็นฐานของทุกเสา** ไม่ใช่เสาที่วางเคียงกัน
2. **One Audit ต้องมาก่อน One Data** การรวมข้อมูลโดยยังไม่มีระบบตรวจสอบ เท่ากับรวมความเสี่ยงไว้ที่เดียว
3. **"One" คือจุดเข้าถึงเดียวในเชิงตรรกะ ไม่ใช่รวมเครื่องเดียว** ข้อมูลยังอยู่ที่ระบบต้นทาง เข้าถึงผ่านบัญชีเดียว API กลาง Portal กลาง และ Log กลาง
4. **ข้อมูลต้องมีเจ้าของ** หน่วยงานต้นทางเป็นเจ้าของข้อมูล งาน IT เป็นผู้ดูแลระบบ
5. **ยกระดับเป็นนโยบายระดับวิทยาเขต** เพราะ One Data, One Service และ One-Brain ต้องให้หน่วยงานอื่นปฏิบัติตาม ซึ่งงาน IT ไม่มีอำนาจสั่งการ

## จุดเด่น

- ตรงกับปัญหาจริง ระบบของวิทยาเขตพัฒนาแยกกัน หลายเทคโนโลยี หลายช่องทาง login
- มีองค์ประกอบพื้นฐานอยู่แล้ว ไม่ได้เริ่มจากศูนย์:
  - มาตรฐานการเชื่อม KU-All Login (OIDC + PKCE)
  - API Gateway กลาง (api.csc)
  - ระบบเฝ้าระวังและแจ้งเตือนกลาง
  - Dashboard พลังงานสำหรับผู้บริหาร
  - คลังความรู้และคลังเอกสารออกแบบระบบ ที่แบ่งชั้นความลับแล้ว
- ชื่อ "ONE" สื่อสารง่าย
- ใช้หลักฐานชุดเดียวกันได้ทั้งงาน PDPA การตรวจสอบภายใน และความเสี่ยงไซเบอร์

## จุดด้อยและความเสี่ยง

1. **หนี้ทางเทคนิคสูง** ยังมีระบบเก่า ซอฟต์แวร์หมดระยะสนับสนุน และบัญชีที่ใช้ร่วมกัน ถ้าเปิดจุดเข้าถึงรวมก่อนแก้ จะเปิดทางเข้ารวมสู่ระบบที่ยังไม่ปลอดภัย
2. **การรวมศูนย์อาจขัดกับ PDPA** ตามหลัก Data Minimization และ Purpose Limitation ต้องมีวัตถุประสงค์รายชุดข้อมูล
3. **ทีมเล็ก ขอบเขตใหญ่** ต้องจัดลำดับ ไม่เช่นนั้นทุกเสาจะคืบหน้าช้าและไม่มีเสาใดเสร็จ
4. **จุดล้มจุดเดียว** SSO, API Gateway และ Log กลางต้องมีสำรอง สำเนานอกเครื่อง และแผนกู้คืน
5. **การเปลี่ยนวิธีทำงานของคน** ต้องมีอำนาจบังคับจากผู้บริหาร
6. **ความเสี่ยงด้าน AI ใน One-Brain** ต้องกำหนดชั้นความลับว่าอะไรส่งให้บริการ AI ภายนอกได้

## ความเป็นไปได้

| เสา | ความเป็นไปได้ | เหตุผล |
| --- | --- | --- |
| One Architecture | สูง | ทำได้ด้วยประกาศและ checklist มีมาตรฐานบางส่วนแล้ว |
| One Audit | สูง-กลาง | มีระบบเฝ้าระวังกลางแล้ว แต่ระบบเก่าส่ง log แบบมีโครงสร้างได้ยาก |
| One Service | กลาง | Portal ทำไม่ยาก แต่ต้องไล่แก้ SSO ของระบบเดิมทีละระบบ |
| One Data | กลาง | API กลางพร้อม ส่วนที่ยากคือคุณภาพข้อมูลต้นทางและการตกลงเรื่องเจ้าของข้อมูล |
| One-Brain | กลาง-สูง (ความรู้ด้าน IT) / ต่ำในระยะสั้น (ทั้งวิทยาเขต) | มีต้นแบบแล้ว การขยายทั้งวิทยาเขตต้องรอเสาอื่นพร้อม |

## โอกาสในการพัฒนาวิทยาเขต

- ผู้บริหารตัดสินใจจากข้อมูลจริง เช่น พลังงาน บุคลากร นิสิต งบประมาณ
- พร้อมรับการตรวจ PDPA ตรวจสอบภายใน ITA และ EdPEx
- ลดต้นทุนและความเสี่ยงจากระบบซ้ำซ้อนและระบบเก่า
- นิสิตและบุคลากร login ครั้งเดียว ใช้บริการจากที่เดียว
- เป็นต้นแบบ digital campus ให้วิทยาเขตอื่น และต่อยอดงานวิจัยหรือการสอนด้าน data/AI
- ความรู้ขององค์กรไม่หายไปเมื่อบุคลากรย้ายงาน

## ข้อแนะนำเพื่อให้เกิดขึ้นจริง

1. ตั้งคณะทำงาน CSC-ONE ที่มีผู้บริหารเป็นประธาน และประกาศเป็นนโยบายวิทยาเขต
2. ส่งมอบ quick win ใน 3 เดือนแรก เช่น Dashboard ผู้บริหาร และหน้ารวมบริการที่ใช้ KU-All Login
3. กำหนดมาตรฐาน One Architecture เป็นเงื่อนไขใน TOR ของระบบที่จ้างภายนอก
4. วัดผลด้วยตัวชี้วัดเชิงตัวเลข และรายงานผู้บริหารทุกไตรมาส
